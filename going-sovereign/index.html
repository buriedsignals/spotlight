Engineering log · Sovereign local tier

Going sovereign.
A full investigation system on a 12B, on my laptop.

Spotlight is a gated, multi-agent OSINT investigation system — an orchestrator that plans methodology, delegates research to an investigator, sends findings through an independent fact-checker, and stops at human review gates. It was built frontier-first. My goal was to make the same system run well on my own machine — a MacBook with 48 GB of unified memory and a 12-billion-parameter open model — with no API calls, no per-token bill, and no source material ever leaving the device. This is the engineering log of how it happened, with the numbers.

Tom Vaillant · Buried Signals · July 2026

Why sovereign matters for newsrooms

Investigative work has two properties that fight the cloud. The material is sensitive — source identities, unpublished findings, documents under embargo — and the workloads are heavy: a single investigation is hundreds of model calls over hours. API-based agents solve capability and create two new problems: every scrape, every name, every hypothesis transits someone else's infrastructure, and the meter runs the whole time. A newsroom that owns its model, its harness, and its data pipeline has neither problem. The question was never whether that's desirable. It was whether a model small enough to run on a reporter's laptop can drive a system this demanding.

The honest answer used to be no. A vanilla 12B collapses on Spotlight's orchestrator prompt. What changed is not the model — it's everything around it. The single most important thing I learned: a small model's failure under an agentic workload is usually an engineering problem wearing a capability costume. Almost every "the model can't do this" turned out to be "the harness is drowning it."

The two discoveries 1 — Procedure tuning beats capability tuning. The 12B doesn't lack knowledge; it loses the procedure — which phase it's in, when to delegate, when to stop at a gate. So we tune on trajectories of the procedure itself, not on domain facts.

2 — Harness engineering is context engineering. Every optimisation below is ultimately one move repeated: keep the working context small, dense, and shaped like the procedure — because a small model's discipline degrades with depth.

01Dynamic skill loading — collapse the floor

Spotlight's methodology lives in skills — markdown procedure files for investigation phases, fact-checking, source acquisition, provenance, ethics. The frontier-shaped approach loads everything up front: every skill body, the full tool catalogue, all instructions. That's a ~55,000-token floor before the first user word, and on a local 12B it costs ~34 seconds of prompt processing before every conversation.

The fix is architectural, not clever: skills are discovered by name and description only; bodies load when a skill is invoked. The orchestrator starts with a catalogue of names, not a library of texts. Measured on this machine:

The same move applies to tools. The open tier's OSINT tool catalogue was an 11,800-token block of permanent context; it's now a local SQLite full-text index (12,500 tools, offline) the model queries with one shell call. Permanent context should be an index, never a payload.

02Harness engineering — one harness, real subagents

Local models don't get a lesser Spotlight. The non-frontier harness is a Flue app built on Pi — and the exact app my evals exercise is the app the installer deploys. That invariant (local test == user experience) sounds bureaucratic until you've debugged a model failure that was actually a deployment divergence. Never build a parallel dev harness.

  • Real delegation: the investigator and fact-checker run in their own child sessions — separate contexts, separate transcripts. Fact-check independence is structural, not a prompt promise.
  • A verb adapter: the skills speak abstract verbs (fetch, search, spawn-agent, query-vault…); a runtime adapter maps them to concrete tools with absolute paths baked in. Two of the nastiest "model failures" in this project were the adapter resolving a relative path or the wrong Python — the model then falls back to something worse (raw curl) and looks stupid.
  • Durable sessions: every conversation persists to SQLite. A crash, a closed laptop lid, a killed process — the same session id resumes exactly where it stopped. Gates become ordinary turns: answer by re-running with the same id.
  • Guard rails for small models: subagents carry an explicit worker guard (never re-delegate — a 12B will happily recurse task→task→task until the run dies), and gates are enforced in the orchestrator's instructions on every path.

03Context optimisation — the RLM and compaction

With the floor collapsed and the harness honest, the remaining killer is growth: context accumulates as the investigation runs, and a small model's behaviour — not just its speed — degrades with depth. I watched the same tuned 12B, in the same session, loop uselessly re-reading files at 40k tokens of context, then reason and delegate crisply at 13k. Depth kills discipline. Two mechanisms keep depth bounded.

Scrapes never enter context raw — the RLM

A scraped page is ~40,000 tokens of navigation chrome, boilerplate, and noise wrapped around maybe 600 tokens of leads. The single biggest failure mode of the local tier was raw pages ballooning the investigator's context. So the harness runs a second, tiny resident model — a Gemma e4b on its own llama.cpp — as an RLM (research language model): every fetch pipes through it automatically and the agent receives a compact, source-linked lead list. The raw page is kept on disk as a .raw sidecar for provenance and citations — compression never destroys evidence.

Crucially this is runtime-automatic, not model-opt-in. An early version asked the model to invoke distillation as a skill; the weak 12B simply never did, and drowned. Anything a small model must do for its own survival belongs in the harness, not in its judgment.

Conversation compaction at the gates

The conversation itself still grows: reasoning, delegations, tool results. But Spotlight's design already contains the answer — each phase writes a compact artifact (methodology.json, findings, fact-check verdicts). The artifacts are the investigation's state; the verbose transcript between gates is disposable. So the harness folds the conversation into a structured checkpoint summary when it crosses a threshold (~16k tokens for the 12B), and — the key trick — the summary is written by the resident e4b, not the main model. The small distiller does double duty as the compaction summarizer.

Measured on a real stalled investigation: an orchestrator context of 40,180 tokens folded to ~10,200 — the e4b read 20.5k tokens and wrote a 1.9k-token checkpoint in about 90 seconds, off the critical path of the main model's two serving slots. The next turn started in the fast zone, and the model that had been thrashing delegated correctly on its next instruction. Compaction turned out to be a behaviour lever wearing a performance-lever costume.

04Procedure tuning, not capability tuning

Here is the discovery I'd offer any newsroom attempting this: don't tune for what the model knows — tune for what it does. Gemma-4 12B already knows what a commercial registry is. What it cannot do out of the box is hold a gated, multi-turn procedure: activate the methodology skill once (not ten times), advance the phase on a bare "approved", delegate instead of doing the research itself, write the artifact, stop at the gate. Those are procedural behaviours, and they can be trained with a tiny dataset if the data is shaped right.

The gold data is actual Spotlight runs: full orchestrator trajectories captured from the real harness — real tool schemas, real delegations, real gate stops, with a stronger model seeding the trajectories and a human approving the gates. Twelve gold trajectories, 30–46k tokens each. The v2 data adds simulated trajectories against the same tool schemas to drill the specific failure modes the evals exposed (phase-advance on bare approval, recovery from a degenerate turn).

What the iterations taught, condensed:

  • v1 (full-text loss): the model learned the style of orchestration — 2.8× faster to a correct first-turn brief — but stalled on the full pipeline, re-activating the skill every turn. Training on tool outputs dilutes the signal you want.
  • v2 (assistant-masked loss, on model turns only): loss fell 3.00 → 0.79 — the model now learns decisions, not tool noise. Getting there required forcing a newer transformers over the training framework's pin, and discovering gemma-4's 2026 chat markers (<|turn>model, not the older <start_of_turn>).
  • The merge bug: an adapter trained in one stack and merged in another produced a model that generated garbage. The merge method must match the training method — and a five-second coherence check before quantisation would have saved a full eval cycle.
  • v3 is the shipping orchestrator. The whole training spend across every iteration, preflight, merge, and quantisation was about ten dollars of rented H100 time. Procedure tuning is cheap because procedures are learnable from few examples.

The model: gemma4-12b-spotlight-orchestrator-v3-GGUF (Q4_K_M, ~7 GB), trained from spotlight-orchestrator-gold.

05KV-cache and serving — the invisible half of local

The most instructive failure of the whole project looked exactly like a model problem: every local eval died around 28–30k tokens, mid-methodology. The logs told the truth — failed to find available cells in kv cache, then failed to restore state with size ~971MB. The model was fine. The serving layer was saving and clearing the orchestrator's KV state every time it delegated to a subagent, then failing to restore it. Small-model agentic serving has its own discipline:

LeverSettingEffect
Resident slots--parallel 2 --no-cache-idle-slotsOrchestrator + active subagent each keep a live slot; nothing saved/restored on delegation. The fix — and counter-intuitively, one slot is worse than two.
KV quantisation--cache-type-k/v q8_0 + --flash-attn on≈½ the KV memory per token — double the effective context in the same RAM, near-lossless.
Context geometry--ctx-size 81920 ÷ 2 slots40,960 tokens per agent — past any point the bounded pipeline reaches.
Reasoning budget--reasoning-budget 400 (12b)Unbounded thinking spends the whole output budget and returns an empty reply (measured: 500 tokens of thought, 0 characters of answer). Capped: think briefly, then act. Scales by tier: 800 for the 26B, 1024 for the 31B.
RLM serving--reasoning-budget 0A distiller/summarizer must answer, not think.

None of this applies to API deployments — the same harness detects the tier and serves frontier/API models unrestricted. The constraints exist exactly where the constraint exists: on the device.

A concrete run, from last night: resuming a real investigation, the tuned 12B — on a bare "Approved, proceed." — reviewed the corpus, delegated, and produced a correct synthesis (the target organisation's president, co-executive directors, and its legal form and domicile), then stopped at the review gate. On my laptop. Nothing left the machine. The marginal cost was electricity.

I want to be precise about the claim: this is not "a 12B is as good as a frontier model." It is that a 12B inside a deeply engineered procedure executes gated multi-agent investigations at usable speed, with the human where the human belongs — at the gates. And every optimisation transfers upward: the 26B and 31B tiers inherit the same harness with looser leashes (later compaction, bigger reasoning budgets, permission to consult raw sources), and run better for it. Tune the procedure for the smallest model, and the bigger ones get it for free.

The recipe, for newsrooms 1 — Collapse the context floor: dynamic skill loading, indexes not payloads.
2 — Engineer the harness: real subagents, absolute paths, durable sessions, one harness for eval and production.
3 — Bound the context: automatic distillation of everything scraped; fold conversations into checkpoints; artifacts on disk are the state.
4 — Tune the procedure, not the capability: a dozen real trajectories with masked loss beat any amount of domain data. Budget: tens of dollars.
5 — Serve deliberately: resident slots, quantised KV, capped reasoning.

Own the model. Own the harness. Own the data. That's sovereignty — and it now fits on a laptop.

Spotlight is open source. The harness, the installer, the skills, and this entire optimisation stack are in the repo; the local tier installs with one script from the setup page. If you're a newsroom trying to go sovereign and you hit a wall, write to me — this log exists so you don't pay for the same lessons twice.
